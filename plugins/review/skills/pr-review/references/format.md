# How the review reads

## Summary (the review body)

First line is the count in backticks, then one short paragraph:

- what the change does and **what you checked and found sound** (name the risky parts you cleared:
  "access is checked before the cache read or the model call");
- then what the findings are about, in one sentence.

```
`1 important, 2 nits`

The new overview route checks access before the cache read or the model call, and the cache key holds
only data every entitled user sees the same way. The one blocker is that the route is allowed during
impersonation although its handler makes a paid model call and writes a row; the nits are two
behaviours with no test that would catch a regression.

---
_Generated by [Claude Code](https://claude.ai/code)_
```

With nothing to raise: `` `No blocking issues.` `` and the paragraph of what you cleared.
On a re-review add one line: "Fixed since the last review: …".

## Inline comment

```
🔴 **Important** — <the problem in one line>.

<Why, with the concrete scenario: which input or state, what the user or system then sees. Name the
files, functions and keys involved in `code`.>

<The fix, or two options if there is a real choice. A `suggestion` block when the fix is a line or two.>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

Same shape with `🟡 **Nit** —` for a nit.

## Tone

- Plain, short sentences. Say what happens, not "this might potentially".
- Quote the project's own rule when you rely on it ("`AGENTS.md` says: …").
- No praise padding, no "great work", no restating the diff.
- One finding per comment. Don't stack unrelated points.
- Don't @-mention people.
